# Detect smoke, fire, and smoking with existing cameras - fully offline

**Keep the current cameras and NVR. Connect RTSP or an existing go2rtc instance, and process video locally without uploading it to a cloud AI service.**

## What it adds

smokefire adds three AI-assisted alert capabilities to an existing video system:

- smoke detection;
- open-flame detection;
- smoking detection.

Potential sites include garment, footwear-material, furniture, packaging, printing, warehouse, logistics, electronics-assembly, and metalworking facilities. It can also support security integrators, low-voltage contractors, and fire-service organizations as an auxiliary video-inspection tool.

| Capability | What it means |
|---|---|
| Existing equipment | Use camera or NVR RTSP feeds without replacing front-end hardware |
| Local offline runtime | Inference, events, and recordings remain on the deployment host |
| Existing go2rtc integration | Configure one API/RTSP base pair and import all main streams automatically |
| CPU / NVIDIA GPU | Prebuilt offline Docker deliveries; no Python or compiler is required on the host |
| Visible capability boundaries | Fixed samples, actual boxes, confidence values, misses, and false detections are documented |

## Existing go2rtc: configure once

Users who already manage cameras in go2rtc do not re-enter feeds one by one:

```text
Customer go2rtc: GET /api/streams
        -> discover main streams; skip _sub / -sub / _sd
smokefire Camera Management
        -> AI detection, evidence, recording, and webhook
```

For go2rtc on the same host, the container-side addresses are usually:

```text
API  http://host.docker.internal:1984
RTSP rtsp://host.docker.internal:8554
```

smokefire reads the stream list but does not modify customer go2rtc configuration. A missing upstream stream disables its managed camera; the camera is restored automatically when the stream returns.

## CPU or GPU

| Delivery | Best fit | Download |
|---|---|---|
| CPU | Evaluation, pilots, smaller deployments, or hosts without NVIDIA GPUs | One complete ZIP |
| NVIDIA GPU | Higher-concurrency requirements | GPU ZIP plus all three image parts |

Compatibility and stream count are not promised by reference to one validation-host GPU model. A GPU host needs an NVIDIA driver, Docker, and NVIDIA Container Toolkit, followed by target-host validation with real feeds for driver compatibility, VRAM use, sustained operation, and capacity.

## Download and deploy

This public repository does not contain the project source tree. Release assets provide source-tree-free runnable deliveries, both model weights, Docker images, startup/verification scripts, and six Chinese/English manuals.

1. Open [Release v1.0.0](https://github.com/newtv-ai/smokefire/releases/tag/v1.0.0).
2. CPU users download `smokefire-deploy-1.0.0-cpu.zip`; GPU users also download the GPU ZIP and every image part.
3. Run `verify.ps1` or `verify.sh`, then `start.ps1` or `start.sh`.
4. Open `http://127.0.0.1:8600` on the service host.

See the [Deployment Guide](docs/smokefire-Deployment-Guide.pdf) for the complete procedure.

## Suggested first pilot

Start with 2-4 representative existing cameras and observe them for 14 days across day, night, backlight, occlusion, distance, and common interference conditions. Review false alerts, missed detections, evidence clips, and resource use before expanding. This is a suggested validation process, not a site-capacity or commercial-service commitment.

For deployment or pilot coordination, [open an Issue](https://github.com/newtv-ai/smokefire/issues/new?title=Deployment%20or%20pilot%20inquiry) with the city, industry, planned feed count, current video integration method, and CPU/GPU environment. No customer case is currently published; real cases will be added only after a pilot and customer permission.
